# Contributing to Minecraft-Eggs

Thanks for helping improve the universal Multi Minecraft egg! This document covers what
contributions look like and how to validate them.

## Ways to contribute

- **Egg improvements**: new engine support, better defaults, installer/launcher fixes
- **Documentation**: anything on [minecraft-eggs.docs.potenfyr.in](https://minecraft-eggs.docs.potenfyr.in) lives in `docs/`
- **Testing**: extend the Docker-based panel behavior suite in `tests/`
- **Bug triage**: reproduce reported issues and confirm engine/version behavior

## Getting started

1. Fork the repository and branch off `master`.
2. The egg is a single JSON file: `egg-minecraft-multi.json` (format `PTDL_v2`). Treat it as the
   **single source of truth**; the docs site builds its catalog from this file at build time.
3. Runtime behavior lives in `run.sh`, `install.sh`, `install-java.sh`, `entrypoint.sh` and the
   `Dockerfile`.

## Egg JSON expectations

`egg-minecraft-multi.json` is generated by the Pterodactyl panel, so keep these invariants when
editing:

- `_comment` marks the file as panel-generated; keep `meta.version` as `PTDL_v2` and
  `meta.update_url` pointing at the canonical raw URL so self-updates keep working.
- `variables[]` entries must define `name`, `env_variable`, `description`, `default_value`,
  `rules`, `user_viewable`, `user_editable`, `field_type`.
- `SERVER_TYPE` validation (`rules: required|string|in:...`) is the authoritative server-type
  list. If you add an engine there, `install.sh` / `run.sh` must handle it, and the docs
  (`docs/src/catalog.ts` server-type registry) should gain a matching entry.
- `docker_images` stays a single universal image; do not split into per-engine images.
- Validate that the file parses as JSON before committing (the panel will refuse malformed eggs):
  `python3 -m json.tool egg-minecraft-multi.json > /dev/null`

## Validation commands

The same commands CI runs (`.github/workflows/docker-image.yml` → `behavior-tests` job):

```bash
docker build -t mc-eggs-test -f tests/Dockerfile.test .
bash tests/panel-test.sh
```

For the docs site (requires [Bun](https://bun.sh)):

```bash
cd docs
bun install
bun run build      # prebuild derives catalog.json from the real egg JSON, then vite builds
bun run dev        # local preview on :5175
```

The docs prebuild reads the actual egg JSON, so if you change egg variables or server types, the
site picks them up automatically; update the curated notes in `docs/src/catalog.ts`
(`SERVER_TYPES`, `JAVA_MAP`) to match.

## Pull requests

- Use the [pull request template](.github/pull_request_template.md).
- One logical change per PR; keep the egg JSON and scripts in sync.
- CI must pass the panel behavior tests (amd64) and the docs build before review.
- Non-trivial changes: open an issue first (use the bug/feature templates) so we can agree on
  the approach.

## Reporting bugs & security issues

- Bugs and regressions: [issue tracker](https://github.com/PotenFYR-Studios/Minecraft-Eggs/issues)
  with the `bug_report` template.
- **Security vulnerabilities: never open a public issue.** Follow
  [SECURITY.md](SECURITY.md) for private disclosure.
